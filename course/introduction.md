# Codex 是如何工作的

学 Java 或 TypeScript，通常从打印一句“Hello World”开始。理解 Codex，也可以从发送一句“你好”开始。

输入框里只有两个字，请求中还有哪些内容？打开这次 Codex Desktop 请求，能看到用户消息、应用指令、工具定义和环境信息。再对照响应，就能把发送的问候与返回的回答对应起来。

## 先认识这个项目

后续实验围绕一个简单的 TypeScript 商品总价项目展开：单价是 10 元，数量是 3，程序却输出 13 元，正确结果应为 30 元。Codex 要找到计算错误，并通过检查确认修改有效。随后继续在这个项目里接入商品目录、增加折扣、安排子任务检查，观察失败或中断后怎样继续。

起始错误位于计算函数：

```typescript
export function calculateTotal(unitPrice: number, quantity: number): number {
  return unitPrice + quantity;
}
```

`10 + 3` 得到 13，期望计算的是 `10 × 3`。两种表达式的返回类型都是 `number`，所以类型检查可以通过，行为测试却会失败。第 3 章中，Codex 根据这个失败结果读取代码、修改运算，再运行检查。

## 选择阅读或亲自复现

**直接阅读无需安装任何工具。** 从第一章开始，对照页面里的对话、截图和工作台；前三章结束时，可以独立找到用户输入、配对工具调用与返回，并判断修复证据是否齐全。

**亲自操作先准备独立项目。** 使用 Node.js 24 或更高版本，复制[故障快照](../examples/01-baseline/README.md)，按其中的命令安装依赖、运行程序和测试。预期程序输出 13、类型检查通过、测试失败；保留这个错误，再将复制后的目录加入 Codex Desktop 项目区，新建任务发送“你好”。

CPA 是本实验中位于 Desktop 与上游服务之间的代理，负责转发和记录模型请求、响应。只有要采集自己的请求日志时才需要配置它。安装和连接方法以 [CLIProxyAPI 项目说明](https://github.com/router-for-me/CLIProxyAPI/blob/main/README_CN.md)及其链接的文档为准；按你的服务设置连接后，先发送一条普通问候，确认日志中的用户文字、请求时间和回答能互相对应，再开始后续实验。不要把只有界面截图当成已采集请求。

后面的[修复版](../examples/07-fixed/README.md)、[MCP 版](../examples/13-mcp/README.md)与[折扣版](../examples/14-discount/README.md)用于对照不同阶段的文件状态。各章的“本章起点”还会说明需要继续原对话还是新建任务；复制文件不会复制聊天历史，回答措辞与调用次数也不要求完全相同。

全书证据的采集环境汇总如下，均可从公开文件核对：

| 项目 | 记录值 | 来源 |

## 从操作到机制

前 3 章依次处理一句问候、一次文件读取和一次修复。把读取操作的调用与返回配对后，就能继续追踪修复时的五次请求，判断每次返回怎样影响下一步。

## 怎样对照证据阅读

工作台中可以展开请求中可见的完整上下文。公开副本已脱敏，未记录的服务端内容不在观察范围内。核对工具是否执行、任务是否完成时，还要查看本地会话记录、项目文件和测试结果。

每次请求的样本日期来自实验索引，模型名称来自请求字段。它们描述当时这次运行；没有逐次记录的 Desktop、CPA 版本不作推定，也不能由请求模型名推断上游部署身份。环境与证据来源可在工作台的“样本与响应信息”和“实验来源与脱敏”中继续核对。

遇到需要核对的字段，可以展开“深入核对”或进入工作台查看完整记录。章末的问题留给你先判断，再展开答案。

网站只在本地记住阅读位置，首页“继续阅读”会带回该位置。读到页末不代表掌握；阶段练习要求你先独立定位和解释，再对照答案。
